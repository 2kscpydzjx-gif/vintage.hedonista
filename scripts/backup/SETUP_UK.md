# Налаштування автоматичних копій Vintazhka

Статус цього пакета: підготовка. Розклад вимкнений, доки `BACKUP_ENABLED` не дорівнює `true`. До першої справжньої копії та контрольного відновлення не вважати систему перевіреною для аварійного розгортання.

Код не змінює робочі товари, схему чи налаштування адмінки. Дружина може редагувати ціни й заміри. Команди відновлення даних у робочу базу не запускаються цим workflow.

## Приватна папка

https://drive.google.com/drive/folders/13ykpAhb_0yL3vHQ9BhxdPp05zOtroZjj

Підпапку `encrypted-repository` створює Restic. Весь вміст репозиторію зашифрований, крім стандартних технічних ознак формату Restic. Не редагувати й не видаляти файли репозиторію вручну. Папку не потрібно робити публічною.

## Одноразові доступи

У GitHub → Settings → Secrets and variables → Actions створити Repository secrets. Самі значення не надсилати в чат, не вставляти у код і не публікувати на Drive.

| Secret | Значення |
| --- | --- |
| `BACKUP_DRIVE_TOKEN` | JSON OAuth-токена Rclone для акаунта, що володіє папкою; потрібен `refresh_token` |
| `BACKUP_RESTIC_PASSWORD` | Довгий унікальний пароль шифрування; додатково зберегти у власному менеджері паролів |
| `BACKUP_DATABASE_URL` | URI-шаблон Supabase Connect → Session pooler, порт 5432, для `yffwjgwwkapdrpwyjwfp`; залишити `[YOUR-PASSWORD]` без підстановки |
| `BACKUP_DATABASE_PASSWORD` | Чинний пароль бази без додаткових лапок; програма сама закодує спецсимволи. Старий формат повного URI з паролем також підтримується, якщо окремий секрет пароля не заданий |
| `BACKUP_STORAGE_ACCESS_KEY` | Access key для S3-сумісного доступу Storage цього проєкту |
| `BACKUP_STORAGE_SECRET_KEY` | Відповідний S3 secret key |
| `BACKUP_SUPABASE_ACCESS_TOKEN` | Особистий Supabase access token із доступом до проєкту для читання розгорнутих Edge Functions |

Підключення Google Drive в чаті не передає постійний доступ до GitHub Actions. Для токена встановити Rclone з офіційного джерела й виконати локально `rclone authorize drive` (у Windows: `.\rclone.exe authorize drive`). У браузері вибрати власний акаунт і перевірити дозволи. Скопіювати отриманий JSON лише у GitHub Secret. Стандартний OAuth-доступ Rclone може охоплювати Drive ширше, ніж одна папка; робоча конфігурація обмежена конкретним `root_folder_id`. За потреби використати окремий обліковий запис для резервних копій.

Існуючий пароль бази не потрібно скидати. Якщо він невідомий, зупинитися й узгодити доступ окремо, а не змінювати його під час роботи магазину.

Після збереження двох секретів бази запустити workflow з `main` у режимі `check-database`. Він експортує лише схему `public` у тимчасову приватну папку, підтверджує підключення та видаляє файл після завершення. Рядки замовлень/користувачів не читаються, нічого не імпортується, Drive та S3 для цього тесту не потрібні. Успішний результат містить `database_connection_verified=true`.

Supabase Storage S3 endpoint: `https://yffwjgwwkapdrpwyjwfp.storage.supabase.co/storage/v1/s3`, регіон `eu-west-1`. Код використовує лише list/copy-from-source, не створює, не оновлює й не видаляє об'єкти у Supabase. Фактичні доступи ключа можуть бути ширшими за операції коду, тому ключі зберігати тільки у Secrets.

## Перший запуск

1. Перевірений PR має бути злитий у `main`. Нові секретовмісні запуски дозволені лише з `main`; PR-тести використовують тільки синтетичні дані без доступів магазину.
2. В Actions відкрити **Encrypted store backup to Google Drive** → Run workflow → `main`, режим `initialize`.
3. Операція створить порожній зашифрований репозиторій і покаже тільки його `repository_id`. Це не ключ розшифрування. Зберегти ID у Repository variable `BACKUP_REPOSITORY_ID`.
4. Запустити режим `backup`. Перший запуск скопіює всі файли, базу, код і розгорнуті функції. Знімок отримає контрольні суми; він буде прочитаний назад із Drive і перевірений.
5. Запустити `backup` ще раз. Якщо фото не змінювалися, `changed_media_files` має дорівнювати 0. База при цьому зберігається новим знімком.
6. Провести окрему перевірку відновлення за `RESTORE_UK.md`: режим `backup-and-test` створює свіжий знімок з об'єднаною схемою та перевіряє реальний імпорт у тимчасовий контейнер без мережі.
7. Задати Repository variable `BACKUP_ENABLED=true`, коли перший повний цикл успішний. Розклад — щодня о 01:35 UTC: 03:35 взимку та 04:35 влітку за часом Києва. GitHub може відкласти scheduled run і може вимикати розклади у неактивних публічних репозиторіях; контролювати історію виконань, розклад не має гарантії точного часу.

Увімкнення чи запуск не змінюють тариф Supabase. Потрібні вільне місце на Drive та доступні квоти GitHub Actions/мережі/Storage.

## Історія та очищення

Нові й змінені фото отримуються зі Supabase, а попередній кеш відновлюється з Drive на тимчасовий сервер. Незмінені блоки повторно на Drive не завантажуються завдяки Restic. Видалення з магазину відобразиться у новому знімку; попередні знімки зберігають старі дані до завершення їх строку зберігання.

Початкове очищення вимкнене. Після успішного контрольного розгортання та узгодження політики встановити `BACKUP_RESTORE_VERIFIED=true`: після успішної недільної копії очищення виконуватиметься автоматично, залишаючи 14 щоденних, 8 тижневих, 6 місячних версій. Режим `retention` також можна запустити вручну. Не встановлювати цю змінну лише через успішний checksum-тест.

Перед копіюванням перевіряється ID наявного репозиторію, після чого виконується штатний `restic unlock` без `--remove-all`. Він прибирає лише застарілі блокування після перерваних процесів; активні блокування залишаються. Якщо сховище все ще заблоковане, операція завершується помилкою з назвою безпечної операції Restic і кодом 11; паролі, імена файлів та сирі діагностичні дані в журнал не потрапляють. Вручну видаляти файли `locks` не потрібно.

Коли резервне копіювання увімкнене через `BACKUP_ENABLED=true`, зміни перевіреного коду `scripts/backup/**` або цього workflow, злиті в `main`, автоматично запускають `backup-and-test`. Так новий код створює свіжу копію та перевіряє імпорт у від'єднаний тестовий контейнер. PR-запуски, як і раніше, використовують лише синтетичні дані.

Помилка доступу до Drive чи неправильний пароль не створюють новий репозиторій замість наявного. Паралельні запуски виключені. Запізнілий або невдалий запуск означає, що остання добра копія старіша; успішний статус обов'язковий для нової копії.

## Межі гарантій

`encrypted_restore_verified=true` означає успішне читання зашифрованого знімка та перевірку його файлів. Це НЕ перевірка імпорту всієї бази в новий Supabase. Повний контрольний імпорт, перевірка платформних Auth/Storage-політик, конфігурацій функцій і зовнішніх сервісів — окремий крок. Поки його не виконано, `full_database_restore_verified` залишається `false`.

Пароль шифрування та ключі сервісів зберігати у менеджері паролів поза цим Drive. Втрата пароля Restic означатиме втрату доступу до копій.
