# Серверні повідомлення про замовлення — підготовлений тестовий пакет

Ці зміни знаходяться в тестовій гілці. Вони **не розгорнуті в робочому Supabase**. Публічний сайт і Vercel preview зараз використовують спільний бекенд, тому розгортання Edge Functions у ньому вплине на обидва сайти незалежно від Git-гілки.

## Підготовлено в коді

- Обидві адреси функцій (`resend-email` і `order-email`) використовують один обробник і шаблон.
- Звичайний клієнт підтверджує JWT через Supabase `auth.getUser`; для повідомлення про нове замовлення додатково перевіряється `user_id`. Збіг email не дає доступу до чужого чи гостьового замовлення.
- Повідомлення про інші статуси з браузера потребує позитивної серверної перевірки `is_admin`.
- Гостьове замовлення обробляється довіреним Database Webhook із окремим секретом. Публічний API key не є доказом права надсилати лист.
- Адреса отримувача береться зі збереженого замовлення, а в тестовому режимі — тільки з `TEST_EMAIL`. Дані webhook про email/ціну/ім'я не використовуються для формування листа.
- Відповіді функції не містять email отримувача, внутрішніх помилок чи відповіді провайдера. Є обмеження розміру запиту, перевірки методу та типу події, екранування HTML і пропуск застарілих подій.
- Обидві адреси використовують один ключ ідемпотентності Resend для серверної версії події замовлення. Міграція `202610280001_order_email_version.sql` додає номер, який змінюється при зміні статусу або виправленні ТТН відправленого замовлення. Тому повернення до попереднього статусу створює новий лист, а повтор тієї самої події використовує той самий ключ. Захист провайдера діє 24 години; довговічний журнал доставок і повтори після тривалих збоїв залишаються окремою серверною роботою.

## Послідовність застосування на окремому тестовому Supabase

1. Підготувати тестовий проект зі схемою, checkout RPC, правилами RLS та тестовими обліковими записами. Не копіювати туди робочі замовлення чи персональні дані. Перевірити резервне копіювання й відновлення до майбутніх змін робочого проекту.
2. Виконати `supabase/audits/prelaunch-readonly.sql`. Скрипт читає лише метадані прав і визначення функцій. Перевірити фактичну перевірку цін, резервування/блокування залишків, права `is_admin`, власні замовлення покупців і недоступність чужих записів. Цей пакет не переписує невідомі робочі політики або RPC.
3. Застосувати `supabase/migrations/202610280001_order_email_version.sql` на тестовому проекті. Міграція не змінює ціни, залишки, покупців або RLS; вона додає серверний лічильник подій. Обробник відмовляється надсилати листи без цього поля. Потім налаштувати секрети Edge Functions за `.env.example`: реальний тестовий ключ Resend, `TEST_MODE=true`, контрольну адресу `TEST_EMAIL`, унікальний випадковий `ORDER_EMAIL_WEBHOOK_SECRET` довжиною від 32 символів. Секрет webhook, ключ Resend і service-role key ніколи не повинні потрапляти у файли браузера.
4. На тестовому проекті розгорнути обидві функції разом із `_shared`. `verify_jwt=false` потрібен для webhook без користувацького JWT; перевірки користувача/секрета виконуються всередині обробника. Саме вимкнення JWT без нового обробника не є захистом.
5. Створити **один** Database Webhook для `public.orders`, подій INSERT та UPDATE. Метод POST, адреса `https://TEST_PROJECT.supabase.co/functions/v1/resend-email`, заголовки `Content-Type: application/json` і `X-VH-Webhook-Secret: <секрет>`. Використовувати стандартний payload Supabase з `schema`, `table`, `type`, `record` та `old_record`. UPDATE без зміни статусу пропускається обробником.
6. Направити **обидві** конфігурації тестового frontend/admin на цей тестовий проект. Лише після налаштування webhook встановити `VH_CONFIG.orderEmailTransport: "webhook"` у них: браузер більше не викликає поштову функцію після покупки чи зміни статусу. Без цього переходу гостьовий виклик браузера отримає 401; спочатку потрібно перевірити webhook.
7. Перевірити гостьову й авторизовану покупки, капсулу, зміни статусів, повторні події, неправильний секрет, чужий ID та збій провайдера. Усі листи мають надходити тільки на тестову адресу. Перевірити автентифікацію також із реальними JWT: локальні тести використовують ізольовані підставні залежності.

Не розгортати лише одну частину цієї схеми в спільний робочий проект. Поточний режим браузерних повідомлень залишено без змін до перевірки окремого бекенда.

## Після появи домена

Підтвердити домен і DNS-записи Resend, встановити `ORDER_EMAIL_FROM` на робочу адресу. При `TEST_MODE=false` обробник відмовляється працювати без налаштованого відправника або з `onboarding@resend.dev`. Перевірити доставку на контрольні реальні адреси перед відкриттям магазину.

## Локальна перевірка

`npm ci --prefix tests --ignore-scripts` встановлює ізольований PostgreSQL/WASM runtime для `node tests/order-email-version.mjs`. Цей тест виконує справжню міграцію й тригер на двох базах у пам’яті, включно зі схемою без необов’язкового поля ТТН. Жодного з’єднання з Supabase немає.

`node tests/order-email-security.mjs` перевіряє реальний обробник зі стандартними Request/Response та ізольованими залежностями, без мережевих звернень, створення замовлень або відправлення листів. Додаткові браузерні тести перевіряють контракт наявного checkout RPC. Вони не замінюють аудит фактично розгорнутих SQL-функцій і RLS.
