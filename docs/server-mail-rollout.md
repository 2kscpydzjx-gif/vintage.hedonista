# Серверні листи про замовлення — розгортання та перевірка

## Фактичний стан — 2026-10-31

У робочому Supabase застосовано міграцію 202610280001_order_email_version
та активовано серверний webhook. Власник виконав SQL через редактор Supabase,
оскільки службові підтвердження інструмента apply_migration прострочувалися.
Запис міграції підтверджено в supabase_migrations.schema_migrations.

Розгорнуто спільний обробник: resend-email v15 і order-email v1.
Код перечитано й звірено з перевіреним runtime-комітом 5917db3.
Неавторизований та неправильний webhook-запити отримують 401; анонімний
виклик hash RPC заборонений. Довірений probe через pg_net для неіснуючого
замовлення отримав 404 без створення рядка або надсилання листа.
Дані orders/products за відбитками не змінилися; Telegram і чинні
тригери резервування збережені. Нових advisory findings для цих функцій немає.

Обидві клієнтські конфігурації в цьому оновленні містять
orderEmailTransport="webhook". До вимкнення TEST_MODE=true власник має
перевірити гостьове замовлення, зміну статусу та скасування на новому сайті.
Раніше він уже підтвердив доставку всіх трьох листів для покупки з акаунтом
і назву Vintazhka; початковий лист №39 мав Delivered і знайшовся в Gmail Inbox.

Сумісний обробник v14 у supabase/rollouts/2026-10-31-resend-domain
залишається історичним знімком для відкату, а не поточним entrypoint.

## Що змінюється

- База ставить подію в pg_net після INSERT або зміни статусу/ТТН.
  Лист для гостьового замовлення не потребує користувацького JWT.
- Міграція 202610280001_order_email_version.sql
  додає лічильник подій, секрет у Vault, RPC для SHA-256 і приватний тригер.
- Новий webhook спочатку **вимкнений**. Повторне застосування зберігає його
  вже встановлений стан і не змінює наявні записи замовлень.
- Секрет генерується всередині бази й не виводиться в SQL-відповідь.
  RPC повертає тільки хеш і доступний лише service_role.
  anon/authenticated не мають доступу до RPC, Vault або приватної функції.
- Payload містить тільки ID, статус і версію. Після перевірки секрету обробник
  читає замовлення з бази; email/ціну/ім'я з webhook він не використовує.
- Обидва endpoint мають спільний обробник і provider idempotency key ID/версія.
  Неактуальні події, оновлення без змін і відправлення без ТТН пропускаються.
- Звичайний браузерний виклик перевіряє JWT через auth.getUser, власника рядка
  та is_admin для зміни статусу. Публічний API key не дає права надсилати лист.
- Ціни, залишки, покупці, чинні RLS і тригери Telegram не переписуються.
  Збій постановки в чергу не скасовує вже прийняте замовлення.

## Ізольовані перевірки

    node tests/order-email-security.mjs
    node tests/order-email-version.mjs
    node tests/order-mail-pipeline.mjs
    node tests/resend-domain-sender.mjs

PGlite виконує справжні PostgreSQL DDL, ACL і тригери. Тестовими замінниками є
тільки Vault/pgcrypto/pg_net; мережевих викликів і робочих даних немає.
Наскрізний тест: анонімний INSERT → тригер → перевірка хешу → обробник → підставний
Resend. Перевіряються ACL, мінімальний payload, тестовий отримувач, статуси/ТТН,
дублікати, застарілі події, rollback і збереження замовлення після збою черги.

Браузерні тести перевіряють Buy, кошик і капсули: існуючий checkout RPC
та перевірки ціни/залишку зберігаються, frontend не дублює серверний лист.

## Порядок розгортання та повторної перевірки

1. Залишити TEST_MODE=true і контрольний TEST_EMAIL. Зберегти відбитки orders
   та перевірити чинні міграції, тригери й резервне копіювання.
2. Застосувати міграцію. Перевірити незмінність записів, ACL service-only RPC
   і те, що zz_vh_order_email_webhook вимкнений.
3. Розгорнути обидва endpoint із supabase/functions разом зі спільними файлами.
   verify_jwt=false потрібен для webhook; авторизація виконується всередині
   нового обробника. Не вимикати gateway JWT на сумісному v14 обробнику.
4. Перечитати розгорнутий код. Без Authorization і з неправильним секретом
   має бути 401. Анонімний виклик hash RPC має бути заборонений.
5. Виконати службовий probe через pg_net із Vault-секретом і неіснуючим ID.
   Очікується 404 від обробника: рядок не створюється, лист не надсилається,
   секрет не виводиться в журнал або клієнт.
6. Виконати activate-server-mail.sql. Перевірити рівно один активний webhook
   та незмінність тригерів Telegram і резервування товарів.
7. Після активації опублікувати обидві конфігурації з transport="webhook".
   До цього короткого переходу браузер і webhook використовують однаковий
   provider idempotency key для захисту від дублювання.
8. Власник перевіряє одне гостьове замовлення, зміну статусу й скасування.
   Листи мають надходити лише на контрольну адресу з назвою Vintazhka.
   Лише після цього переводити TEST_MODE=false.

## Відкат

deactivate-server-mail.sql вимикає лише новий webhook. Повернути сумісний
обробник v14 із verify_jwt=true та прибрати transport="webhook" з обох
конфігурацій. Лічильник і секрет можна залишити: відкат не видаляє історію,
замовлення або Vault і не зачіпає Telegram.

## Межі перевірки

Локальні тести не доводять роботу hosted Vault/pg_net або доставку у скриньку.
Для цього потрібні робочий probe без листа та контрольний гостьовий тест.
pg_net працює асинхронно. Довговічний журнал доставок і автоматичні повтори
після тривалих збоїв провайдера тут не реалізовані. Resend дедуплікує ключі
протягом 24 годин; це не гарантія exactly-once після цього вікна.
