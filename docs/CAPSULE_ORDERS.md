# Одне замовлення для повної капсули

Виправлення готується в окремій тестовій гілці від main після PR #136. Робоча база й уже створені замовлення не змінюються.

## Причина

Код пов'язував ідентичність капсули зі спеціальною ціною двічі:

- `capsules-front.js` записував `capsule_offer` лише для першого образу й лише якщо `capsule.price > 0`.
- `site.js` передавав `p_capsule_id`/`p_look_id` лише за наявності одного запису знижки. Навіть повна капсула з окремою ціною, що дорівнює сумі речей, переходила в звичайну гілку замовлення товарів.

Читання відкритого каталогу 27 жовтня підтвердило, що чотири з п'яти активних капсул мають окрему ціну 0: їхня вартість на сторінці складається з цін речей. Для них перша умова прибирала прив'язку вже при додаванні в кошик. Обидві умови існували до випуску повної контактної форми; попередній тест перевіряв лише капсулу зі знижкою та заздалегідь записаною прив'язкою, тому не охоплював цей випадок.

## Поведінка

Повний головний образ отримує `capsule_offer` незалежно від спеціальної ціни. Головний образ визначається через `is_main` і розташовується першим; його ідентичність не залежить від порядку рядків у відповіді.

Розрахунок повертає повні капсули окремо від знижок. Цінова поведінка клієнта збережена: за додатної вигіднішої ціни застосовується знижка; без неї залишається сума речей. Для повної капсули виклик чинного RPC завжди містить `p_capsule_id`, `p_look_id` та повний список `p_product_ids`. Сигнатура RPC, передача контактів/доставки та механізм резервування не змінюються.

Якщо головний образ або його склад змінився, капсула неактивна, частину речей видалено чи втрачено частину прив'язок, оформлення зупиняється перед RPC з поясненням. Прив'язка не видаляється мовчки. Змішані кошики й кілька повних капсул пропонують оформити окремо, оскільки чинний виклик підтримує одну капсулу. Звичайні товари й альтернативні образи зберігають попередній шлях.

Старий кошик без прив'язки не перетворюється на капсулу за самою лише подібністю товарів: це могло б змінити намір звичайного покупця. Повторне додавання головного образу відновлює прив'язку вже наявних речей без дублювання. Для перевірки preview капсулу слід додати зі сторінки капсули заново.

## Перевірки й межі

`tests/capsule-orders.cjs` проходить саме сторінку капсули → додавання → боковий кошик → checkout → RPC payload → читання батьківського замовлення й п'яти рядків у реальній розмітці адмінки, включно з reload. Окремо охоплює ціну 0, знижку, ціну рівну/вищу від суми, main не першим у джерелі, старий кошик, змінені зв'язки, неповну/неактивну капсулу, змішаний кошик, втрату прив'язки одного товару та звичайні замовлення. Модель RPC навмисно повертає окремі замовлення для звичайного шляху, щоб тест помітив відсутність capsule ID. Замовлення, рядки та листи ізольовані; фактичне виконання серверної функції й її цінова поведінка при ціні 0 цим тестом не підтверджуються.

Додатковий локальний огляд з чинними відкритими даними перевіряє всі п'ять капсул до межі RPC. Виклик створення перехоплюється й зупиняється до мережевого запису. Локальні звіти — в ігнорованій папці `work/capsule-orders`. SQL не виконується; реальні замовлення та листи не створюються, попередні розділені замовлення не об'єднуються автоматично.

Новий набір включено в CI; зміни `capsules-front.js` запускають його. Публічні посилання на `site.js` та `capsules-front.js` мають версію кешу 290.
