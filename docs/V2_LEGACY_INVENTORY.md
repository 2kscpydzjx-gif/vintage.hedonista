# Vintage Hedonista — інвентаризація V1/V2 (19.10.2026)

Статус: **кодова інвентаризація, без видалення файлів і без змін поведінки**. Потрібна перевірка в браузері перед міграцією.

## Підтверджені зв'язки

| Файл | Спостереження | Рішення |
| --- | --- | --- |
| admin/admin.html | Має посилання на v2-editor.html | Перевірити реальний маршрут із меню |
| admin/v2-editor.html | Meta refresh на cms-builder.html | Legacy redirect; не видаляти до зміни навігації |
| admin/cms-builder.html | Підключає cms-builder.js і cms-studio.js | Діючий механізм даних; поки залишити |
| admin/v2-cms-builder.html | Підключає cms-builder.js, не v2-cms-builder.js | Перевірити, чи v2-cms-builder.js взагалі використовується |
| admin/cms-studio-v2.html | Підключає cms-builder.js, cms-studio.js, cms-v2.js | V2 використовує стару логіку |
| admin/cms-v2.js | Коментар: presentation only, save/publish in cms-builder.js | Не вважати окремим рушієм збереження |
| admin/v2-cms-bridge.js | Створює прихований iframe на v2-cms-builder.html | Перевірити подвоєний рендер/синхронізацію |
| admin/cms-builder.js | localStorage + vh_page_revisions (draft/published) у Supabase | Перевірити пріоритет даних, ревізії та F5 |
| admin/v2-cms-builder.js | Окрема велика копія CMS-логіки | Кандидат на видалення лише після перевірки посилань |
| site.js | Є legacy і V2 механізми відображення | Визначити один published source перед вимкненням legacy |

## Ризики та невизначеність
- Сам факт наявності кількох файлів **не доводить**, що всі одночасно виконуються.
- Наявність прихованого iframe **не доводить**, що саме він спричиняє мерехтіння; потрібні runtime-тести.
- Не підтверджено, що кожен старий блок можна видалити без міграції збереженого контенту.

## Безпечний порядок змін
1. У браузері зафіксувати маршрут Admin → Конструктор і активні JS-ресурси (Network/Performance).
2. Експортувати ревізії й блоки для сторінок Home, About, Contacts, Capsules/Styles та зняти скриншоти до змін.
3. Перевірити порядок: Supabase published/draft → localStorage → iframe → site.js; відтворити F5, autosave, publish, image swap, pan/zoom.
4. Обрати затверджений V2 як єдиний UI, зберігши працездатний CMS data engine до міграції.
5. Окремими малими PR прибрати redirect/дубльовані маршрути, зайві reload і подвійне застосування блоків.
6. Після регресії та підтвердження, що дані мігровані, окремим PR видалити непотрібні legacy-файли.

## Критерії готовності
- Один видимий редактор V2, один опублікований стан сторінки, без legacy flash.
- Збереження та публікація працюють після F5; фото не мерехтять; прев'ю відповідає опублікованій сторінці.
- Немає втрати блоків, фото, текстів, стилів, товарів і капсул.

Наступний крок: перевірка фактичного маршруту та життєвого циклу редактора; не починати масове видалення до цих тестів.
