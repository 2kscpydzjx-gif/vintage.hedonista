# Перше тестове розгортання Cloudflare Pages

Підготовлено в `codex/prelaunch-mobile-polish`. Основний сайт, DNS і спільна база цим пакетом не перемикаються. Контрольна позначка до адаптації Cloudflare: `seo-vintazhka-prehosting-2026-10-31`.

## Підключення тестового проєкту

1. У Cloudflare відкрити **Workers & Pages** → створення застосунку → **Pages** → підключення Git-репозиторію. Назви пунктів можуть відрізнятися; обирати Pages із Git, а не Worker із командою `wrangler deploy`.
2. Підключити GitHub, надавши доступ лише до `2kscpydzjx-gif/vintage.hedonista`.
3. Вибрати такі налаштування:

| Поле | Значення |
| --- | --- |
| Project name | `vintazhka-test` або інша вільна тестова назва |
| Production branch | `codex/prelaunch-mobile-polish` — лише в окремому тестовому проєкті |
| Framework preset | None |
| Build command | `npm run build:cloudflare:test` |
| Build output directory | `dist` |
| Root directory | Корінь репозиторію; поле залишити порожнім, якщо це стандартне значення |
| Environment variable | `NODE_VERSION` = `22` |

Не додавати Supabase service-role, Resend або Telegram secrets: у цій статичній збірці вони не потрібні. Наявний publishable key є публічною клієнтською конфігурацією; серверні ключі повинні залишатися на сервері.

4. Створити розгортання та перевірити Build log. Очікуються `cloudflare: true`, `preview: true`, `readOnlyData: true`, `siteUrl: https://vintazhka.com.ua/`.
5. Відкрити отриману адресу `*.pages.dev`. **Не підключати vintazhka.com.ua або www до цього тестового проєкту.**

Позначення Production branch у Cloudflare означає основну адресу саме цього проєкту. Примусова команда `build:cloudflare:test` залишає цей проєкт тестовим і без запису навіть для гілки з назвою `main`.

## Що забезпечує тестова збірка

- `noindex,nofollow,noarchive` у HTML та `_headers`, `Disallow: /` у robots. Захист `*.pages.dev` доданий також для майбутнього основного проєкту.
- Блокування стандартних клієнтських запитів запису у спільний Supabase: товари, заміри, чернетки/публікації, замовлення, файли й виклики Edge Functions. Вхід, оновлення сесії, перевірка `is_admin` і читання дозволені. Відновлення пароля/реєстраційні листи у тесті не надсилаються.
- У конструкторі вимкнені серверні Save/Publish; редагування й локальні чернетки/експорт залишаються доступними. Заміри працюють локально. Частина інших кнопок запису може показати повідомлення про тестовий режим, не виконуючи запит на сервер.
- Це захист від випадкових дій у звичайному інтерфейсі, **не серверна ізоляція або заміна RLS**. Для повного тестування збереження/оформлення потрібен окремий тестовий Supabase; довільні дії через консоль браузера не захищаються цим режимом.
- Усі вкладені файли, JS/CSS та навігація включені до `dist`. Кореневий `404.html` не дозволяє Cloudflare підміняти неіснуючі адреси головною сторінкою як у SPA.
- `cms-shell.js` застосовує опубліковані спільні налаштування шапки й підвалу також на товарах, статтях, оформленні, у кабінеті та сторінках капсул. На звичайних CMS-сторінках він використовує вже отриману публікацію без повторного запиту; на окремих сторінках читає лише `home/published.shared`, не застосовуючи блоки головної й не завантажуючи модель редактора. Локальні тестові чернетки не публікуються.
- Меню присутнє з актуальними назвами вже в початковому HTML: Cloudflare-збірка робить read-only запит опублікованої навігації. Якщо цей запит недоступний, використовується збережений публічний знімок `scripts/published-navigation.json`. Після входу на сторінку звичайне читання публікації залишається авторитетним. Кеш новішої публікації застосовується до першого кадру; старіший кеш не підміняє новішу збірку. Для ізольованих тестів `VH_NAVIGATION_SNAPSHOT_FILE` вказує локальний JSON замість мережевого запиту. У збірку не переносяться локальні чернетки чи зміни даних у Supabase.

## Адреси Cloudflare

Cloudflare Pages перенаправляє `/contacts.html` на `/contacts`, а `/seo-product/назва/index.html` на `/seo-product/назва/`. Файли й slug не перейменовані. У Cloudflare-збірці canonical, OG URL, sitemap, Product/Offer/Breadcrumb JSON-LD використовують кінцеві адреси; конструктор, категорії, журнал та анімації розпізнають обидва формати. Збірки для чинного GitHub/Vercel зберігають попередній формат.

## Перевірка після першого розгортання

1. Відкрити головну, каталог, категорію/підкатегорію, товар, журнал/статтю, контакти й доставку. Перевірити фото, меню та мобільні розміри.
2. Перевірити актуальні опубліковані CMS-блоки, анімації та відсутність нескінченного приховування сторінок після перенаправлення на чисту адресу.
3. Відкрити адмінку та конструктор. Побачити тестове попередження, disabled Save/Publish, локальний перегляд/чернетку. Не використовувати це розгортання для робочого наповнення.
4. Перевірити справжню HTTP 404 для вигаданої адреси, X-Robots-Tag та robots. Локальні тести моделюють маршрути Pages; відповіді Cloudflare перевіряються окремо після створення проєкту.

## Основний проєкт — наступний етап після погодження

Окремий Pages-проєкт: production branch `main`, build command `npm run build:domain`, output `dist`, Node 22. `CF_PAGES=1` і `CF_PAGES_BRANCH` визначають платформу та гілку автоматично. Гілки, відмінні від `main`, працюють у режимі preview без запису. Для іншої production-гілки потрібно явно задати `VH_PRODUCTION_BRANCH`.

Сюди згодом підключаються `vintazhka.com.ua` та перенаправлення з www. Це не виконується тестовим пакетом. Потрібні окрема перевірка нового хостингу, Auth URL/поштового домену, SEO та план переходу зі старої адреси. Переносити локальні тестові чернетки в публікації автоматично не можна.

Офіційні довідки: [Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/), [Build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/), [Serving Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/), [Headers](https://developers.cloudflare.com/pages/configuration/headers/).
