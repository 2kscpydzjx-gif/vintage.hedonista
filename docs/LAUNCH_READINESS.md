# Підготовка до запуску — 26 жовтня 2026

## Відновлення пароля

У формі входу є «Забули пароль?». Лист Supabase Auth веде на `account.html` у корені поточного сайту, включно з переходами з вкладених SEO-сторінок. Сторінка з recovery-сесією відкриває форму нового пароля замість кабінету. Є підтвердження пароля, обробка помилок сервісу, повторний запит простроченого посилання й очищення hash після обробки SDK. Адміністративна сесія не використовується.

Форма приймає recovery event після ініціалізації SDK; незавершений запит даних кабінету не перезаписує її. Auth-виклики не очікуються всередині auth callback, щоб уникнути блокування SDK.

`tests/password-recovery.cjs` перевіряє UI → виклики Auth → відповідь → UI з ізольованою сесією на ПК/телефоні, помилки, прострочення, повторний лист та гонку з кабінетом. Реальні листи й паролі користувачів тест не змінює. Доставку справжнього recovery-листа та список дозволених Redirect URLs потрібно перевірити в сесії власника. Використано той самий `account.html`, що вже використовується для підтвердження реєстрації. Після придбання домену його адреса має бути дозволена в Supabase Auth.

## SEO

Генератор заповнює editorial-секцію за її ID, зберігаючи атрибути конструктора. Він більше не залежить від точного набору/порядку атрибутів HTML. Відновлено статичні описи дев'яти категорій і 18 підкатегорій; пріоритет збережених редактором SEO-текстів не змінюється. Відсутність секції спричиняє помилку генерації, а аудит перевіряє початковий видимий H2/опис.

Кабінет, оформлення та HTML-сторінки адмінки мають `noindex`. Заголовок checkout — «Оформлення замовлення». Публічні canonical, sitemap і поточний домен збережені. Перевірено 142 SEO-сторінки, 149 адрес sitemap та статичні посилання на всі 106 товарів.

## Швидкість

Каталог запитує поля, які використовує для карток, пошуку й фільтрів, замість усіх колонок товару. Збережені повний опис для пошуку, кольори/сезони/розміри, категорії, статуси та всі фото для hover/fallback.

На однакових 106 товарах відкритого API під час перевірки JSON-відповідь зменшилась із 575 439 до 479 605 байтів: 95 834 байти, або 16,7%. Це розмір відповіді до HTTP-стиснення, а не відсоток прискорення всього сайту. Головна запускає незалежні запити вмісту паралельно з налаштуваннями. `tests/storefront-performance.cjs` блокує відповідь settings і перевіряє, що вміст уже запитується; також перевіряє пошук, сортування, категорії, статуси й фото на ПК/телефоні.

Перший показ, інтро, геометрія блоків та анімації перевіряються окремими регресійними наборами. Фактичний LCP/INP/CLS живого сайту на мобільній мережі тут не вимірювався: доступ до публічного GitHub Pages з браузерного середовища обмежений. Повний CSS не видалявся без доказу невикористання правил. Результат оптимізації зображень і хостингу потрібно виміряти на остаточному домені.

## Поява карток товарів

Каталог, вкладені SEO-категорії та нові надходження на головній використовують спільну появу карток: прозорість, вертикальне зміщення 24 px і 800 ms із коротким каскадом у рядку. Реєстрація відбувається після готовності CMS та завершення інтро; нижні й приховані каруселлю картки чекають входу у видиму область. Стандартні ефекти збережені для інших блоків; custom/none та reduced motion мають пріоритет.

Після фільтрації/сортування нова добірка з'являється плавно. «Показати ще» додає наступні картки без перебудови вже показаних вузлів і повторного запуску їхнього ефекту. Старий pulse сітки й поява всього carousel-контейнера не накладаються на новий рух. `tests/product-card-motion.cjs` перевіряє проміжні opacity/transform, прокручування, фільтри/сортування, збереження DOM при підвантаженні, реальні URL категорій, інтро й вимкнення ефектів на ПК/телефоні.

## Межі змін

Ціни, контакти, опубліковані CMS-ревізії, робота замовлень, Resend, схема та дані Supabase не змінюються. Генератор SEO лише читає відкриті дані й записує локальні HTML-файли. Випуск коду не публікує тестові чернетки.
