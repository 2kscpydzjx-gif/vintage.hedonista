# Підготовка SEO до vintazhka.com.ua

Основний домен: **https://vintazhka.com.ua/**. DNS, NS, HTTPS, облікові записи та основний сайт цими змінами не налаштовуються. Хостинг ще не обраний.

## Що підготовлено

- `launch-site.json` задає майбутню адресу. Поточний `config.js` і вихідний sitemap зберігають адресу GitHub Pages до перенесення.
- Збірка для домену одночасно змінює `siteUrl`, canonical, OG URL, статичні Product/Offer JSON-LD, організацію/посилання політики повернення, sitemap та robots у `dist`. Динамічна розмітка використовує цю саму адресу з конфігурації.
- Назви та шляхи товарів, статей, категорій і підкатегорій збережені. `/seo-product/…/index.html` працює на звичайному статичному хостингу; приховування цієї частини URL зараз не потрібне.
- Основна адреса головної на новому домені — `/`. Адреса `/index.html` може відкривати ту саму сторінку, але її canonical веде на `/`.
- Вкладені SEO-сторінки використовують відносний `<base>` і посилання навігації, щоб фото, стилі, скрипти та переходи працювали на тому хості, де відкрито сайт. Canonical при цьому залишається абсолютним.
- Preview та існуючий тестовий Vercel-проєкт мають `noindex,nofollow,noarchive` у HTML і `Disallow: /` у robots; на `*.vercel.app` також діє наявний X-Robots-Tag. Canonical нового домену не відкриває тестову версію для індексації.
- Кабінет, оформлення й адмінка зберігають `noindex` у звичайній збірці для домену й не включені в sitemap. `robots.txt` не замінює авторизацію.

Приклади відповідності:

| Раніше | На новому домені |
| --- | --- |
| `https://2kscpydzjx-gif.github.io/vintage.hedonista/index.html` | `https://vintazhka.com.ua/` |
| `…/vintage.hedonista/catalog.html` | `https://vintazhka.com.ua/catalog.html` |
| `…/vintage.hedonista/seo-product/vovnyanyi-zhaket-kardyhan/index.html` | `https://vintazhka.com.ua/seo-product/vovnyanyi-zhaket-kardyhan/index.html` |

## Перевірка і збірка

Виконувати з кореня репозиторію, Node.js 22+:

```sh
npm ci --ignore-scripts
node tests/hosting-build.mjs
node tests/seo-domain.cjs
```

Тести працюють з локальними файлами та ізольованими даними. Вони перевіряють відповідність усіх поточних 149 URL, збереження заголовків/контенту, статичні посилання на 106 товарів, вкладені ресурси, canonical після застосування SEO з адмінки/фільтрації, Product/Breadcrumb JSON-LD та захист preview. Після тестів `dist` повертається до звичайної збірки поточного сайту.

**Коли домен і хостинг готові**, створити кінцевий артефакт:

```sh
npm run build:domain
npm run audit:domain
```

Завантажувати **вміст `dist/` у корінь сайту**, зі збереженням усіх вкладених папок. Не завантажувати весь репозиторій і не додавати каталог `/vintage.hedonista/` на новому хості. Звичайний `npm run build` поки зберігає поточний домен; `build:domain` явно обирає адресу з `launch-site.json`.

У preview/test-середовищі захист індексації має пріоритет навіть над `build:domain`. Публічний хостинг не повинен мати `VERCEL_ENV=preview` або ідентифікатор тестового проєкту. Якщо залишимо Vercel для основного сайту, команду збірки для домену встановимо лише в основному проєкті після узгодження перенесення.

## Під час підключення хостингу

1. Визначити ціль DNS-записів за інструкцією обраного хостингу. Якщо DNS веде Cloudflare, NS у реєстратора мають відповідати двом серверам, призначеним Cloudflare цьому домену.
2. Увімкнути HTTPS і постійне перенаправлення HTTP → HTTPS та `www.vintazhka.com.ua` → `vintazhka.com.ua`. Зберігати шлях і query; не перенаправляти всі товари на головну. За можливості додати 301 `/index.html` → `/` окремо від вкладених `index.html` товарів.
3. Перевірити на справжньому сервері `/`, каталог, вкладений товар, статтю, категорію з українським slug, фото/стилі/скрипти, sitemap, robots та справжню 404 для неіснуючої адреси. Не вмикати загальну SPA-підміну невідомих адрес головною.
4. Перевірити, що публічні сторінки нового домену не мають `noindex` у HTML або X-Robots-Tag. Не знімати `noindex` з адмінки/кабінету/оформлення й тестового проєкту.
5. Вирішити перенесення з GitHub Pages: серверні 301 на старій адресі залежать від можливостей старого хоста. Підготовлена відповідність URL сама по собі не створює перенаправлень. Не вимикати старий сайт до перевірки нового; потім узгоджено налаштувати старі canonical/перехід і уникнути двох індексованих копій.
6. Окремо оновити дозволені Auth/відновлення пароля URL і поштові налаштування Resend, перевірити реальні сценарії. Це не змінюється SEO-збіркою.
7. Підтвердити новий домен у Google Search Console, подати `https://vintazhka.com.ua/sitemap.xml`, перевірити кілька URL. Попередній HTML verification-token не замінює підтвердження права на новий домен.

Фактичні відповіді сервера, 301, TLS, DNS і доступ Google до нового домену перевіряються після підключення. Підготовка файлів не підтверджує їхню роботу на ще не обраному хостингу.
